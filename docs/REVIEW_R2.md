## T1 🔴 `check-detail-logic.js`：图表标题可以**全部为空**，测试照样绿

### 问题

原断言只有一条：`check(mismatch === 0, ...)`。而 `mismatch` 只在
**成功从 `chartStat` 里正则提取出数字之后**才可能自增（原第 74、80 行）：

```js
const m = d2.chartStat.match(/([+-][\d.]+%)\s*$/);
const chartPct = m ? m[1] : null;
...
} else if (chartPct && chartPct !== grid) { mismatch++; }
```

`chartPct` 为 null 时整条分支跳过。**零次比较 = 零个不一致 = 通过。**

顺带：成功时打印的 `"15 个组合全部一致 ✅"` 里的 15 是**手写常量**，不是数出来的。
实际参与比对的只有 **12** 个——韩国「近5年」格子是「—」，三个口径共 3 个组合从来不比。
**这句话本身就已经是假的了。**

### 复现（已验证）

把 `detail.js` 第 184 行的标题改成空串：

```bash
perl -0pi -e 's/stat = `\$\{pts\[0\]\[0\]\} → \$\{pts\[pts\.length - 1\]\[0\]\} · \$\{fmt\(snapV\)\}`;/stat = "";/' miniprogram/pages/detail/detail.js
node scripts/check-detail-logic.js
```

改坏之后的输出：

```
图表标题 vs 各区间涨幅格子（全部区间 × 全部口径）:
  15 个组合全部一致 ✅
...
✅ 详情页逻辑全部通过        ← 退出码 0
```

**这正是上一轮那条 40.49pt 的失效模式换了一层**：上一轮是桩没跑到被测代码，
这一轮桩是忠实的，但**断言不检查自己有没有真的比过**。

### 修法（我已经改了，代码在仓库里）

```js
let mismatch = 0, compared = 0;
...
} else if (!chartPct) {
  mismatch++; console.log(`  ✗ ${cur} ${label}: 格子 ${grid}，图表标题却取不出数字「${d2.chartStat}」`);
} else {
  compared++;
  if (chartPct !== grid) { mismatch++; ... }
}
...
check(compared >= 12, `只真正比对了 ${compared} 个组合（应 ≥12）——标题没取出数字`);
```

改完的实测：

```
基线:    退出码 0     →  「12 个组合逐项比对，0 处不一致 ✅」
改坏后:  退出码 1     →  「图表与格子有 12 处不一致 / 只真正比对了 0 个组合（应 ≥12）」
还原后:  退出码 0
```

**新风险**：`compared >= 12` 也是一个手写下限。当某个指数的可比窗口变多变少时会误报。
更稳的做法是把断言写成「格子非「—」的组合数 === compared」，我没这么写是因为
这个脚本只测 KS11 一个指数，写成自洽等式会掩盖「格子突然全变成「—」」这种退化。
12 这个数字应该在指数池或窗口定义变动时被主动复核——这一点我在代码注释里写了。

## T2 🔴 `check-cdn-hedge.js`：把对冲**整个拆掉**，它还是绿的

### 问题

两处：

1. **预算常数对不上**。测试里 `BUDGET_MS = 3000`，而 `cdn.js` 里 `BUDGET = 2500`。
   也就是说测试允许被测代码**超出自己的预算 500ms**。而 3000ms 是云函数被杀的
   硬线——一个在 `fetchJSON` 内部就用满 3000ms 的函数，加上冷启动和 `JSON.parse`
   早就死了。**断言画在死亡线上，不是设计线上。**
2. **失败分支完全不断言**。第 37 行的 `catch` 只 `console.log`，不 `fails.push`，
   也不检查耗时。注释第 7 行写着「断言每种情形都在 3 秒预算内收敛」——
   **对失败的两种情形，这条断言不存在**。而失败情形正是线上 5/20 的那一类。

### 复现（已验证）

把对冲的点火定时器拆掉（等价于回退这次修复的核心）：

```bash
perl -0pi -e 's/const timer = setTimeout\(startBackup, HEDGE_AT\);/const timer = null;/' cloudfunctions/lib/cdn.js
node scripts/check-cdn-hedge.js; echo "退出码 $?"
```

输出：

```
主源挂起: 用了 cdn.jsdelivr.net，耗时 2803ms，...      ← 超了自己的 2500 预算
...
✅ 取数对冲全部符合预期
退出码: 0
```

**2803ms**。加上冷启动，这就是线上那 11/20 次 `-504003`。测试绿着。

### 修法

```js
const BUDGET_MS = 2500;                 // 与 cdn.js 的 BUDGET 保持同一个数，最好直接 require 出来
...
}catch(e){
  const ms = Date.now()-T0;

  if(ms >= BUDGET_MS) fails.push(`${name} 失败也用了 ${ms}ms，超出预算`);

```

那不是误报——它说明 `BUDGET` 本身就该再降（见 `A9`）。

## A1 🔴 「指数数量下降即 exit 1」的守卫是死代码 —— 防护第三次够不着

### 问题

`build-data.js:166`：

```js
const prevSnapPath = path.join(OUT, "prev-snapshot.json");
if (fs.existsSync(prevSnapPath)) { ... process.exit(1); }
```

而 `dist/prev-snapshot.json`：

- **`build-data.js` 从不写它**（全文只有这一处引用，是读）
- **`daily.yml` 从不下载它**（「取回上一轮」那一步只 `curl` 了 `dist/fx.json`）
- **本机 `dist/` 里不存在**

所以 `existsSync` 恒为 false，整块守卫永远不执行。

### 复现（已验证）

```bash
grep -n "prev-snapshot" scripts/build-data.js .github/workflows/daily.yml
#  → scripts/build-data.js:166  （只有这一行，是读）
ls dist/prev-snapshot.json
#  → No such file or directory
node scripts/build-data.js     # 完整构建，守卫这一段一次都没进去
```

### 为什么这条排在很前面

这是**唯一**能发现「某个市场悄悄从榜单消失」的机制。
没有它，单个指数抓取失败 → 被 `INDICES.filter(m => series[m.code])` 静默过滤 →
快照少一行 → 副标题从「27 个国家」变成「26 个国家」→ 没有任何人会注意到。
而 `freshEnough`/`staleNote` 那条路在这种情况下**完全不会触发**：构建成功了，
`generated` 是新的，数据也是新的，只是少了一个国家。

这是「写了防护但防护够不着」的第三个实例（前两个是 `fx.js` 的 `partial`
和 `cdn.js` 的串行兜底）。同一种病，三次了。

### 修法

`daily.yml` 里多下一个文件，`build-data.js` 里多写一个文件：

```yaml
- name: 取回上一轮产物（增量与守卫用）
  run: |
    mkdir -p dist
    curl -sf -m 30 -o dist/fx.json            "https://raw.githubusercontent.com/${GITHUB_REPOSITORY}/data/fx.json" || true
    curl -sf -m 30 -o dist/prev-snapshot.json "https://raw.githubusercontent.com/${GITHUB_REPOSITORY}/data/snapshot.json" || true
```

```js
// build-data.js：写完 snapshot.json 之后
fs.copyFileSync(path.join(OUT, "snapshot.json"), path.join(OUT, "prev-snapshot.json"));
```

**新风险**：`prev-snapshot.json` 会跟着 `dist/` 一起被推到 `data` 分支（多 52 KB）。
无害，但要知道它在那儿；也可以在推送前 `rm`。
另一个风险：守卫是「只要少一个就 exit 1」，一旦新浪某天抽风，**当天就不发布任何数据**，
用户看到的是昨天的数据 + 36 小时后的 `staleNote`。这是对的取舍（宁可停更也不要
悄悄少一个国家），但要有人看 Actions 的红灯——建议同时加一条
`if: failure()` 的通知步骤，否则守卫生效了也只是红在没人看的地方。

## A2 🔴 `cdn.js` 的 gzip 分支上 `res` 没有 error 监听器 —— 响应流中途出错会让云函数直接挂掉

### 问题

`cdn.js:41-49`：

```js
const chunks = [];
const st = res.headers["content-encoding"] === "gzip" ? res.pipe(zlib.createGunzip()) : res;
st.on("data", ...);
st.on("end",  ...);
st.on("error", reject);      // ← 只挂在 st 上
```

- **非 gzip 时** `st === res`，`st.on("error")` 就是 `res.on("error")`，安全。
- **gzip 时** `st` 是 gunzip 流。`pipe()` **不转发源流的错误**。
  于是 `res` 上一个 error 监听器都没有 → 响应流中途出错（socket hang up /
  ECONNRESET / 提前关闭）→ Node 抛未捕获异常 → **整个云函数进程挂掉**。

而上面 T3 已经实测：**线上两个源都返回 gzip**。也就是说这条唯一在生产跑的分支
是唯一没有错误防护的分支。

### 复现（已验证）

我桩掉 https，让响应先吐半截 gzip 再在 `res` 上 emit error：

```bash
node /tmp/gziptest.js
```
```
ok:       ✅ 成功 {"a":1}
badgzip:  ⛔ 被拒「... incorrect header check ...」      ← gunzip 自己的错能捕获
💥 未捕获异常，云函数会直接挂掉： socket hang up
退出码 9
```

`badgzip` 那行证明 `st.on("error")` 对 **gunzip 的**错误是有效的；
崩溃的是 **`res` 的**错误。

**验证程度**：崩溃是我用桩确定性复现的（桩里的 `res.pipe` 按 Node 的真实语义写，
不转发源错误）。「线上真的会在响应中途断流」这一点我**没有实测**，
只能说这是移动端/机房网络上的常见故障模式。

### 后果比看上去糟

函数挂掉返回的不是 `-504003`，所以 `utils/cloud.js` 的 `isTimeout()` 是 false，
**不会重试**。用户直接看到错误页。而且它挂在对冲的一条腿上——
本来另一条腿可能已经成功了，现在整个进程没了。**对冲在最该救命的时候被绕过。**

### 修法

一行：

```js
}, (res) => {
  res.on("error", reject);            // ← 加这行，放在重定向判断之前
  if ([301,302,307,308].includes(res.statusCode) && res.headers.location) { ... }
```

**新风险**：几乎没有。`reject` 幂等（Promise 只兑现一次），非 gzip 路径会多挂一个
监听器指向同一个 `reject`，无副作用。
顺带把 T3 的桩补上 gzip 情形，否则这个修法没有测试保护。

## A3 🔴 令牌漏了 `load()`：开详情页后立刻切区间 → **永久**的图表/数值错配

### 问题

`detail.js:76`：

```js
this.chart = await this.loadChart(RANGES[this.data.rangeIdx]);
this.render();
```

**没有令牌。** 而 `onRange` 的守卫是 `if (!this.snap || !this.m) return;`，
`this.snap` 在第 58 行就已经赋值——**远在第 76 行的 `await` 之前**。
所以用户完全可以在初始图表还在路上时切区间。

于是：初始那个请求（**冷启动那次，最慢的一次**）后返回，
无条件覆盖 `this.chart` 并 `render()`。`rangeIdx` 已经是新的了。

### 复现（已验证，跑的是真实 `detail.js`）

```bash
node /tmp/race2.js      # 让初始「近1年」慢 400ms，60ms 后用户切到「近3年」
```
```
A 切换后立即:   区间=近3年 标题「2023-09-15 → 2026-09-18 · +134.74%」跨度=1099天   ← 正确
A 慢请求返回后: 区间=近3年 标题「2025-09-18 → 2026-09-18 · +134.74%」跨度=365天   ← 错了
                格子=+134.74%
❌ A：停在「近3年」，标题跨度却只有 365 天 —— load() 的旧曲线覆盖了新曲线
```

**365 天的日期区间配 3 年的涨幅，画的是 1 年的曲线。**
这和 STATUS 里记录的线上症状（「选中『近1年』，标题却是 3 个月的日期配 +88.17%」）
是同一个 bug，只是换了入口。

**而且它不是瞬时的**——没有任何后续渲染会纠正它。上一轮修掉的那个至少
在下一次切换时会自愈，这个不会。

### 为什么它比 onRange 那条更容易在线上发生

初始 `load()` 里的 `get-chart` 是**冷启动之后的第二个请求**，是整条链路上最慢的。
而「打开详情页，第一眼看到的是近1年，立刻想看近3年」是最自然的操作。

### 修法

给 `load()` 也发一张票：

```js
const token = ++this.rangeToken;
const c = await this.loadChart(RANGES[this.data.rangeIdx]);
if (token !== this.rangeToken) return;      // 用户已经切走了，这张票作废
this.chart = c;
this.render();
```

**更好的修法（同时修掉 A4）**：别让 `render()` 相信 `this.data.rangeIdx`。
把曲线和它所属的区间绑在一起：

```js
// 写 this.chart 时一并写 this.chartRange
this.chart = c; this.chartRange = RANGES[next];
// render() 里
const R = this.chartRange;                  // 而不是 RANGES[this.data.rangeIdx]
```

这样**无论哪条异步路径写进来，标题和曲线永远出自同一个区间**，
从结构上消除这一类 bug，而不是每发现一条就补一个守卫。

**新风险**：`R` 与 picker 显示的区间在请求在途期间会不一致（picker 说近3年、
标题还是近1年的）。这其实是正确的——数据还没到就不该假装到了——
但要配一个「加载中」的视觉状态，否则用户会以为切换没生效。
`chartLoading` 已经有了，把 `chartStat` 也一起置灰即可。

1. **阈值提到 14 天**。14 覆盖台湾最长的农历新年休市，同时仍然挡得住

## A7 🟡 对冲把 jsDelivr 拉回了主路径，而 `chart/` 与 `monthly.json` **从来没被 purge 过**

这是你最担心的那条。**风险是真的，而且有一个你没提到的放大器。**

### 放大器：purge 列表从上一轮起就没动过

`.github/workflows/daily.yml:56`：

```bash
for f in snapshot.json fx.json series.json; do
```

**`monthly.json` 不在里面。`chart/*.json` 不在里面。**（上一轮我提过，没修。）

在对冲之前这无所谓——jsDelivr 是串行兜底，几乎轮不到它。
对冲之后它是**并发的第二条腿，900ms 就点火**，赢面很大。
于是：
- `snapshot.json` 每天被 purge，jsDelivr 上的版本相对新；
- `chart/KS11.json` **从来没被 purge 过**，jsDelivr 上的版本可能落后不止一天。

### 它会以什么形式被用户看见

正是上一轮 `A3` 那对冤家，换了个成因：

| 组件 | 数据来源 | 可能来自 |
|---|---|---|
| 详情页标题的涨幅 | 快照（`R.winKey`） | raw，今天 |
| 详情页的曲线、起止日期 | `chart/{code}.json` | jsDelivr，可能是上一版 |

结果：标题写着 `2025-09-18 → 2026-09-18 · +87.53%`，而曲线的最后一点是 09-17。
更隐蔽的是 `detail.js:99` 的 `from = minusMonths(this.m.asof, r.months)`——
`m.asof` 来自**快照**，拿去裁**另一个版本**的图表数据。

首页的自定义月度区间同理：`meta`/`baseAsof` 来自快照，月末点位来自 `monthly.json`。

### `freshEnough(36h)` 挡不住 —— 而且是按构造挡不住

`freshEnough` 的 36 小时阈值是**为了容忍一天构建失败**才定的。
而 jsDelivr 回上一版数据，正好就是「落后一个构建」= 约 24 小时。
**两者同量级。** 用一个为了容忍 24 小时陈旧而设的阈值去检测 24 小时的陈旧，
逻辑上就不可能成立。

更要命的是：**`chart/*.json` 里根本没有 `generated` 字段**，
`get-chart` 也不回传任何新鲜度信息。就算客户端想检查，也没东西可查：

```bash
curl -s --compressed ".../chart/KS11.json" | head -c 200
# {"code":"KS11","ccy":"KRW","n":...,"dates":[...]   ← 没有 generated
```

（今天两个源的内容是一致的——最近一次推送才几小时，jsDelivr 还没机会陈旧。
所以**这条我没有在线上抓到实例**，是按机制推断 + purge 列表实证。）

### `HEDGE_AT=900` / `BUDGET=2500` 有没有更有道理的取法

**`HEDGE_AT = 900` 其实取得有道理，别改。** STATUS 里实测 raw 取 52 KB 快照
是 0.43–0.80 秒，900ms 刚好在观测上界之上——含义是「主源健康时几乎不点火备源」，
这正是你想要的（因为备源可能陈旧）。这比拍脑袋强。

**要改的是两件别的事**：

1. **`HEDGE_AT` 应该随文件大小走。** 那个 0.43–0.80s 是 52 KB 的 `snapshot.json`
   测出来的。`series/{code}.json` 最大 144 KB，合理耗时本来就更长，
   用同一个 900ms 会**在大文件上频繁误点火**，恰好在最该用新鲜数据的地方
   把陈旧的 jsDelivr 拉进来。建议 `HEDGE_AT = 700 + 预期KB * 3`，或者按文件分档。
2. **`BUDGET = 2500` 没给冷启动留位置。** 注释说「留 300ms 给冷启动与 JSON.parse」，
   但 `BUDGET` 是从 `fetchJSON` **开始**计时的，冷启动发生在它之前、不在这 2500ms 里。
   零依赖函数的冷启动实测在数百毫秒量级，2500 + 冷启动 + parse 会摸到甚至越过 3000。
   **线上残留的那 1/20 次超时大概率就是这个。**
   修法：模块级 `let warm = false`，首次调用用更紧的预算：
   ```js
   let warm = false;
   async function fetchJSON(file) {
     const BUDGET = warm ? 2500 : 1700;     // 冷启动那次自己让出时间
     const HEDGE_AT = warm ? 900 : 500;
     warm = true;
     ...
   }
   ```

### 有没有既保成功率又保同源的办法

有，而且比「带 build id 回查」便宜得多。**按我的推荐顺序**：

**① 第一条对冲腿打到同一个源（推荐，改动最小）**

线上 11/20 的失败是**连接级挂起**，不是 raw 整体宕机。
那么第一条对冲腿就不该换源——**再开一条到 `raw.githubusercontent.com` 的连接**即可。
新连接大概率走到另一个 CDN 节点，挂起问题解决，而**版本一致性零风险**。
jsDelivr 降级成第三条腿，1600ms 才点火，真正只在 raw 整体不可用时出场。

```js
const legs = (f) => [
  [`https://raw.githubusercontent.com/${REPO}/data/${f}`, 0],
  [`https://raw.githubusercontent.com/${REPO}/data/${f}`, 900],   // 同源第二条连接
  [`https://cdn.jsdelivr.net/gh/${REPO}@data/${f}`,      1600],   // 真·最后手段
];
```
代价：多一个 socket。**收益：99% 的对冲场景不再引入第二个版本的真相。**

**② 把 `monthly.json` 与 `chart/*.json` 加进 purge 列表（一行，必做）**

```bash
for f in snapshot.json monthly.json fx.json series.json $(ls dist/chart | sed 's|^|chart/|'); do
```
33 个 chart 文件 = 33 次 purge 请求，Actions 里几秒钟。
这不能根治（purge 对分支引用本来就不可靠），但把「可能落后很多版」
压回「最多落后一版」。

**③ 让每个产物都带 `generated`，客户端只检测不重取（兜底）**

`build-data.js` 给 `chart/{code}.json` 和每个 series 分片都写上同一个 `generated`；
`get-chart` 原样回传。`detail.js` 比对两者，不一致就**不重取**（没有预算），
只在图下面加一行「走势数据来自上一版构建（MM-DD）」。

**代价说明**（你问的）：
- 重取 = 第二次云函数往返 = 至少 +1 秒，冷启动时直接撞 3 秒。**不可行。**
- 只检测 = 零额外往返，只多一个字段和一次字符串比较。**这是免费版唯一能做的。**

**④ 不推荐：jsDelivr 用 commit SHA 固定引用**

`cdn.jsdelivr.net/gh/user/repo@<sha>/file` 是不可变引用，jsDelivr 会正确缓存，
陈旧问题彻底消失。但 SHA 要等 `git commit` 之后才知道，而它又得写进
被提交的 `snapshot.json` 里——循环依赖，得用两次提交或指针文件绕。
**为了一条最后手段的腿做这些不值当，选 ① 更划算。**

## A9 🟡 自定义月度区间：终点选第一项 → `m0Idx = -1` → 标题「undefined 月末」、空榜、无提示

### 问题

上一轮 A10 的互相约束引入了两个边界错误（`index.js:120-130`）：

```js
onM1(e) {
  const j = +e.detail.value;
  this.setData({ m1Idx: j, m0Idx: Math.min(this.data.m0Idx, j - 1), ... });
}
```
`j === 0` 时 `m0Idx = -1`。

```js
onM0(e) {
  const i = +e.detail.value;
  const j = Math.max(i + 1, this.data.m1Idx);
  this.setData({ m0Idx: i, m1Idx: Math.min(j, len - 1), ... });
}
```
`i === len-1` 时 `j = len`，被 `Math.min` 压回 `len-1` = `i` → **起止同月**，
而这正是上一轮那条修复明确要禁掉的情形。

### 复现（已验证，跑的是真实 `index.js`）

```bash
node /tmp/months.js
```
```
用例 1：终点 picker 选第一项（index 0）
    m0Idx=-1 m1Idx=0  标题「undefined 月末 → 2020-09 · 人民币口径 · 0 个市场参与排名」
    前3: (空)  | （统计行也是空的）

用例 2：起点 picker 选最后一项（index n-1）
    m0Idx=72 m1Idx=72  标题「2026-09 月末 → 2026-09 · 人民币口径 · 12 个市场参与排名」
    前3: 中国 0.00%  中国香港 0.00%  中国台湾 0.00%  | 0 涨 0 跌 12 平 · 中位数 0.00%
```

用例 1 的界面是：一个写着 **undefined** 的标题 + 一张空榜 + 没有任何解释。
用例 2 是上一轮明确要禁掉的「起止同月」又回来了。

### 修法

两个 handler 都要同时夹紧自己和对方：

```js
onM0(e) {
  const n = this.data.monthOptions.length;
  const i = Math.min(+e.detail.value, n - 2);          // 起点最多只能到倒数第二个月
  const j = Math.max(i + 1, this.data.m1Idx);
  this.setData({ m0Idx: i, m1Idx: Math.min(j, n - 1), expanded: "" });
  this.render();
},
onM1(e) {
  const j = Math.max(+e.detail.value, 1);              // 终点最少是第二个月
  this.setData({ m1Idx: j, m0Idx: Math.min(this.data.m0Idx, j - 1), expanded: "" });
  this.render();
},
```

**新风险**：夹紧之后 picker 显示的值和用户选的值会不一致
（选了第一项、结果跳到第二项），这会让人以为点错了。
更好的做法是干脆把不合法的项从 `range` 里去掉：起点 picker 只列
`months.slice(0, n-1)`，终点 picker 只列 `months.slice(m0Idx+1)`。

## A10 🟡 重试策略：详情页最坏 19.2 秒只显示「加载中…」；且不重试网络失败

### 问题（已验证：读代码 + 算术）

`utils/cloud.js`：3 次尝试、间隔 300ms、单次上限是云函数被杀的 3000ms。

```
首页 get-snapshot 最坏:              3×3000 + 2×300 = 9600 ms
详情页 get-snapshot + get-chart 串行: 19200 ms
期间界面：只有「加载中…」，无进度、无「第 N 次重试」
```

按你实测的一成失败率：三次全挂的概率约 0.1%（可以接受），
但**每 10 次打开就有 1 次要多等约 3.3 秒，且屏幕上什么都不说**。

另外 `isTimeout` 只匹配 `-504003` 和 `/timed out/i`：

- 手机信号抖动导致的 `request:fail` **不重试**——而这在移动端至少和冷启动超时一样常见。
- `A2` 那种函数崩溃返回的错误也**不匹配**，于是也不重试。

### 修法

1. `call()` 多接一个 `onRetry` 回调，页面据此把「加载中…」改成
   「云函数冷启动中，正在重试（2/3）…」。**这比缩短重试更有用**——
   等待本身是可接受的，无声的等待不是。
2. 重试条件放宽到 `request:fail` 与网络类错误（它们同样幂等）。
   但**要区分**：超时重试可以立刻（函数已被预热），网络失败应该退避
   （300ms → 800ms）。
3. 详情页的两个请求可以**并发**而不是串行：`get-chart` 的 `from` 依赖
   `m.asof`……这确实依赖快照。退一步：先用客户端本地日期算一个保守的 `from`
   并发打出去，拿到快照后若 `asof` 与假设不符再补一次。收益不大，**不建议做**。

## A12 🟢 频率校验截断到日历年边界，并把 `meta.start` 变成一句假话

### 问题（已验证）

`build-data.js:83-86`：截断点取的是「稀疏年之后第一个观测」，
也就是**下一个日历年的第一天**。

但巴基斯坦源里日频数据其实是 **2023-11-16** 开始的：

```
2023-11-01 2023-11-16 2023-11-17 2023-11-20 2023-11-21 ...  ← 11-16 起就是日频了
```

实测构建输出：

```
⚠️ 巴基斯坦 卡拉奇KSE100: 2023 年及以前为月频（每年 42 条），已截断，丢弃 74 条，日频自 2024-01-01 起
dist: KSE100 现在的起点: 2024-01-01   meta.start: 2024-01-01
```

**2023-11-16 → 2023-12-29 那约 30 个完全正常的日频点被一起丢掉了**，
代价是「近3年」要晚 1.5 个月才恢复。注释说「截到该稀疏年之后第一个观测密度正常的日期」，
代码做的是「截到下一个日历年的第一个观测」。

更值得说的是**诚实性**：截断之后 `meta.start = 2024-01-01`，
而界面上「数据不足」区的行内文案直接渲染它：

```
巴基斯坦 · 卡拉奇KSE100（数据自 2024-01-01 起） —
```

**这是一句关于数据源的假话。** 源里有 2020 年起的数据，是我们丢掉的。
用户无从得知，也无从判断这个判断是否合理。

### 「截断」和「保留但标注」哪个更诚实

**截断是对的，但当前的实现不诚实。** 理由：

- 保留月频数据的话，窗口起点落在离月频点 10 天以内的概率约 1/3，
  于是巴基斯坦会**每天在榜单里闪进闪出**（今天有「近3年」、明天没有）。
  一个不稳定的榜单比一个稳定缺席的榜单更糟。
- 但截断必须被**记录并展示**。加一个 `meta.truncatedFrom`，行内文案改成
  「早期为月频数据，已剔除；日频自 2024-01-01 起」。
  这样用户知道发生了什么，也知道这是我们的判断而不是源的限制。

### 修法

```js
// 找密度转折点，而不是日历年边界
const after = ks.filter((d) => d.slice(0,4) > cutYear);
// 往前回看：从稀疏年的末尾开始，找到第一个「其后 20 个观测平均间隔 < 3 天」的点
const inCut = ks.filter((d) => d.slice(0,4) === cutYear);
let cut = after[0];
for (let i = 0; i + 20 < inCut.length; i++) {
  const gap = (new Date(inCut[i+20]) - new Date(inCut[i])) / 86400000 / 20;
  if (gap < 3) { cut = inCut[i]; break; }
}
```
并把 `truncatedFrom: ks[0]` 写进 meta。

**新风险**：密度转折点的判定本身是启发式的，可能把一段真实的高频行情误判成转折。
20 个观测的窗口对这个数据量是够的，但这类启发式应该把判定结果打到构建日志里
（现在已经有 `freqNotes` 了，扩一下就行），让人能事后复核。

对冲之前这无所谓（jsDelivr 是串行兜底，几乎轮不到）；
对冲之后它是 900ms 就点火的第二条腿。于是详情页的标题（快照，raw，今天）
和曲线（chart，jsDelivr，可能落后不止一版）可以来自不同的构建——
**正是上一轮 A3 那对冤家，换了个成因**。

`freshEnough(36h)` 按构造挡不住：那个阈值是为了容忍一天构建失败才定的，
而 jsDelivr 回上一版正好就是约 24 小时。更根本的是 **`chart/*.json` 里
连 `generated` 字段都没有**，客户端就算想查也没东西可查。

我的推荐是**第一条对冲腿打到同一个源**（再开一条 raw 连接），
因为线上 11/20 的失败是连接级挂起、不是 raw 宕机。这样 99% 的对冲场景
不再引入第二个版本的真相，jsDelivr 退到 1600ms 才点火的第三条腿。
再把 purge 列表补全（一行）、给每个产物写上 `generated`（只检测不重取，零往返）。

> **紧随其后的第四名是 `A2`**（`cdn.js` gzip 分支上 `res` 没有 error 监听器，
> 响应流中途出错会让云函数直接挂掉，实测退出码 9）。
> 它没进前三只是因为触发频率不明；但它有两个放大属性：
> 一是**它只存在于线上 100% 会走的那条分支**（两个源都返回 gzip，我实测了响应头），
> 二是**它返回的错误不匹配 `isTimeout`，所以 `utils/cloud.js` 不会重试**。
> 修法是一行 `res.on("error", reject)`。
>
> 与之配套的是 `T3`：`check-cdn-hedge.js` 的桩从不设 `content-encoding: gzip`，
> **唯一跑在生产的分支，是唯一没被测的分支**。先补桩，再修代码。
