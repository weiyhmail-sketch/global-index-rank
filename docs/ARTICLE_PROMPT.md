> 用法：开一个新的 Claude Code session，工作目录设为本项目根目录
> `~/Desktop/AI工程项目/指数小程序`，把下面 ``` 之间的内容整段贴进去。

---

```
你的任务是把这个项目写成一篇公众号文章。

先说清楚这不是什么：**不是 README 的复述，不是项目介绍，不是功能清单。**
公众号读者不关心「我做了一个支持三种计价口径的指数排行榜」，
他们关心的是有没有一个他们没想到的东西。

这个项目里最值钱的那个东西是：**我让 AI 审查 AI 写的代码，两轮下来，
最狠的发现不是某个数算错了，而是「验证」本身是假的。**

## 先把材料读完再动笔

按这个顺序读，不要跳：

1. `docs/STATUS.md` —— 最长，但故事都在里面。特别是末尾几节：两轮审查的
   完整账本，包含我承认自己判断错了的地方。
2. `docs/ADVERSARIAL_REVIEW.md` —— 第一轮审查报告（22 条）
3. `docs/REVIEW_R2.md` —— 第二轮，靶子是第一轮的修复本身
4. `README.md` —— 背景与架构
5. `git log --stat` —— 提交信息里写了每个修复的推理过程，比代码本身更有信息量

**所有数字必须从仓库里核出来，一个都不许编。** 你写进文章的每个百分比、
每个条数、每个耗时，都要能在代码、文档或 `dist/` 的产物里找到出处。
拿不准的就去跑一下：七个检查脚本都能直接跑（见 README「用法」一节）。

## 建议的骨架（可以调整，但要先有理由）

**开场用一个具体的、外行也能看懂的错。**

候选：「近3年 · 人民币」榜单的前三名，**没有一个是人民币**。
台湾、埃及、巴基斯坦的原币涨幅混进了人民币榜，因为缺汇率的市场退回了原币值
还参与排名——而缺汇率的恰恰是货币在贬值的新兴市场，原币数必然偏高、必然浮到榜首。
修复前后的榜单对比在 STATUS 里，自己去核准确数字。

这个开场的好处：不需要任何技术背景就能感到不对劲，而且它是**单边偏差**——
不是随机误差，是必然把错的顶到最显眼的位置。

**中段是主线：测试在撒谎。**

两个实例，都要写具体：

- 第一轮：给云函数写的桩忽略了一个参数，永远返回整份文件，
  于是被测代码一次都没跑到，而我在文档里写着「图表与榜单一致性 ✅」。
  实际最大偏差多少个百分点，去 `docs/ADVERSARIAL_REVIEW.md` 核。
- 第二轮：一致性断言不检查自己有没有真的比过。把图表标题整个改成空串，
  它照样打印「N 个组合全部一致 ✅」——实际比对 **0 次**，
  而那个 N 还是手写死的常量，跟真实可比数对不上。

配套的那个模式也要写：**写下防护 → 不验证它会不会触发 → 记一笔「已修」。**
四个实例在 STATUS 里列着，挑两个写透比四个都提一遍强。
其中最好的一个是：为了防止「某个市场悄悄从榜单消失」而加的守卫，
写完之后**从来没有运行过**——它依赖的文件没人写、没人下载、根本不存在。

**结尾给一个可迁移的东西，不要停在「我修了很多 bug」。**

可以用的落点（挑一个，别都写）：
- 通过的测试不等于代码是对的，要先怀疑测试。
- 每加一道防护，就写一个让它触发的用例；不然只是写了个心安。
- 让 AI 审查自己的产出有效，但第二轮必须把靶子对准第一轮的修复——
  因为修复和验证修复的测试，出自同一个人之手。

## 有几件事必须诚实地写进去

1. **这个产品公开发不出去。** 个人主体在微信里做不了金融类目，
   换企业主体后 A 股数据又需要两家交易所的信息经营许可合同。
   README 里有按官方文档逐条核过的说明。**不要在文章里留二维码或体验链接**，
   目前只有 15 人白名单的体验版。这个结局本身是文章的一部分，不是瑕疵。
2. **不构成投资建议。** 文章里出现任何涨跌数字时，都是在讲数据处理，
   不是在讲市场。不要写任何带方向判断的话。
3. **代码是 AI 写的，bug 也是 AI 写的，找出 bug 的也是 AI。**
   不要把这写成「AI 很厉害」或者「AI 不行」。真实情况更有意思：
   AI 很擅长写出**看起来被验证过**的代码，而这恰恰是最难发现的失败形态。

## 风格要求

- **不要 AI 腔。** 不写「在当今这个……的时代」「让我们一起来看看」
  「这不仅仅是……更是……」。不用排比句撑场面。
- 不要用「赋能」「闭环」「抓手」这类词。
- 段落短，一段讲一件事。代码片段要真的能对上仓库里的内容，别为了好看改写。
- 中英文之间、中文与数字之间留空格。
- 长度 2000-3500 字之间。超过 3500 字读者会掉。
- 标题给 3 个候选，标出你推荐哪个、为什么。

## 输出

写成 `docs/ARTICLE.md`，可以直接粘进公众号编辑器的格式
（不要用公众号不支持的 Markdown 特性，比如表格的复杂对齐、脚注）。

文末单独列一节「本文事实核对」，把文章里出现的每个关键数字
对应到仓库里的哪个文件或哪条命令。这一节我会删掉再发，
但我要用它来确认你没编数字。

写完先别急着收尾，回头问自己一遍：
**如果我是读者，读完这篇有没有拿到一个我原本不知道的东西？**
如果答案是「知道了有人做了个股市排行榜」，那就重写。
