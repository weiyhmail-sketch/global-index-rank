## 更正：东方财富拦的是 TLS 指纹，不是机房 IP（2026-09-20）

此前文档多处写「东财对机房/境外 IP 拒连」，**这个诊断是错的**。逐项实测：

| 客户端 | TLS 实现 | 结果 |
|---|---|---|
| Chrome（同一台机器、同一网络） | BoringSSL | ✅ 完整返回泰国 SET 全年日线 |
| curl 8.7.1 | SecureTransport / LibreSSL | ❌ ECONNRESET |
| **Node https 模块** | OpenSSL | ❌ ECONNRESET |
| 微信云函数（Node） | OpenSSL | ❌ ECONNRESET |

排除过的变量：请求头（裸请求 / UA / UA+Referer / 全套 Chrome 头均失败）、
HTTP 版本（--http1.1 与 --http2 均失败）、URL 形式（带/不带 ut 均失败）、
出口 IP（经代理的 45.76.215.254 与直连的家宽 36.36.210.240 均失败）。

> 顺带确认代理的规则模式工作正常：国内服务看到 36.36.210.240（广东深圳天威视讯），
> 境外服务看到 45.76.215.254。之前怀疑规则没生效也是错的。

**结论**：东财按 TLS 指纹拦截非浏览器客户端。绕过它需要伪装浏览器指纹
（curl-impersonate 一类），属于规避 bot 检测，本项目不采用。
**东财对程序化取数不可用**，与部署在哪、用什么 IP 无关。

这也解释了为什么新浪、腾讯、Frankfurter 等源在云函数里都正常——
它们没有这类检测。

## P4：逐年涨幅 + 数据源顺序修正（2026-09-20）

### 按产品评审做减法

评审把 P4 原定三项判为两砍一缓，本轮照此执行：

| 原计划 | 处置 | 理由 |
|---|---|---|
| 全球热力图 | **砍** | 48 色块 × 375px，手机上是装饰不是信息 |
| 分年度矩阵 | **改做** | 48 行 × 10 列只能横滚，而横滚表格是移动端最差交互。改为详情页里单个指数的**逐年竖排列表**，回答同一个问题，成本低一个数量级 |
| 分享长图 | **缓** | 前置依赖正式发布——体验版转出去是别人点不开的死图 |

逐年涨幅直接复用各年 12 月末点位，不另取数据。
校验：当年那行与快照 YTD 逐项一致；切换计价口径后逐年随之变化。

### jsDelivr 不适合频繁更新的数据（重要）

实测：Actions 推送新版后云函数仍拿到上一版。手动 purge 返回 `finished`、
两个 provider 都清了、响应头 `x-cache: MISS` 确认回源，**内容依旧是旧的**。

原因是 **jsDelivr 会缓存「分支名 → commit」的解析结果**，purge 单个文件
并不会让它重新解析分支 HEAD。分支型 jsDelivr URL 因此不能用于日更数据。

改为 `raw.githubusercontent.com` 优先、jsDelivr 兜底。
实测 raw 并不慢：52 KB 快照 gzip 后仅 9210 字节，0.43–0.80 秒。

### 验证

新增 `scripts/check-detail-logic.js`，用真实数据在 Node 里跑详情页 render()。
模拟器交互验证不稳定（点击时有时无），而风险都在 JS 计算侧。

首页已在模拟器实机确认：数据加载、结论条、榜单、名次变化角标均正常，
控制台零报错，启动 830ms。重试机制生效（冷启动首次失败后自动重试成功）。

## 模拟器实机验证通过（2026-09-20）

此前多轮因自动化通道不稳而未验证的视觉渲染，本次用 computer-use 直接驱动
开发者工具完成，**抓到三个只有真跑才会暴露的问题**。

### 一、模拟器启动失败：`Cannot read property 'subPackages' of undefined`

根因是 `project.config.json` 里 `libVersion: "latest"` —— 该工具**并不解析
"latest"**，而本机只下载了 3.15.2 / 3.16.1 / 3.16.2 / 3.17.2 四个基础库，
解析不到具体版本时运行时配置为 undefined。改为明确写 `3.17.2` 后立即正常。

> 参考：同机跑通的「灵感速记」项目用的是 `libVersion: "3.0.0"`，也是明确版本。

### 二、列表里国名被压成两行

`.country` 在 flex 容器中被挤换行（「韩/国」「澳大/利亚」）。
加 `white-space: nowrap; flex: none`，让指数名去承担压缩。

### 三、每一行都挂着多余的「截至 09-18」

`dataAsof` 取全体最大值。而**埃及交易所是周日到周四交易**，
它的最新日常常比其余市场晚一到两天；以它为基准，另外 32 行全被标注。
改用**众数**作基准后，只有真正的异常项才标。

> 顺带修正一个我自己的误判：起初看到「数据截至 2026-09-20（周日）」以为是
> 数据 bug，查证后发现中东市场周日开盘，数据是对的。

### 四、冷启动超时在真实运行中发生

模拟器首屏直接报 `-504003 FUNCTIONS_TIME_LIMIT_EXCEEDED` —— 这正是此前
推断过但未实测的风险，**每天第一个用户都会撞上**。

新增 `miniprogram/utils/cloud.js`：超时自动重试（默认 3 次，间隔 300ms）。
失败的那次调用本身已把函数预热，重试通常 1-2 秒返回；所有读取函数都是
纯查询、幂等，重试无副作用。

## 免费方案定型（2026-09-20）

用户要求尽量走免费路，围绕「云函数 3 秒超时不可调」重构了数据读取层。

### 关键发现：重依赖是冷启动杀手

| 云函数 | 依赖 | 首次调用 |
|---|---|---|
| `ingest` | wx-server-sdk（为写数据库） | ❌ 连续 4 次超时 |
| `get-monthly` | 无 | ✅ 1430ms |

据此把**所有读取函数改为零依赖、直接从 CDN 取构建产物**，不再经数据库。
`get-snapshot` 1493ms、`get-monthly` 1801ms、`get-series` 1054ms，**首次调用均成功**。

代价：每次客户端请求都要回源 CDN（jsDelivr 有缓存，实测很快）；
好处：去掉了数据库、定时触发器与冷启动脆弱性，配置负担归零。

### 数据分片

| 文件 | 体积 | 用途 |
|---|---|---|
| `snapshot.json` | 40 KB | 首屏排行榜（含 meta/快照/名次变化） |
| `monthly.json` | 59 KB | 各月末点位，打开自定义区间时按需取 |
| `series/{code}.json` | 19–144 KB | 单指数日线，详情图按需取 |
| `series.json` | 1.13 MB | 整包，仅本地调试用 |

拆分依据全是实测：整包 series gzip 后 329 KB / 2.57 秒、汇率表 254 KB / 3.9 秒，
都撞 3 秒超时；monthly 占快照六成体积而首屏用不到。

### 自定义区间的解法

汇率表和整包序列都进不来，任意日期区间在免费版下无解。
改为**预计算各月末点位**（三种口径，6 年 73 个月），客户端自算任意两月之间的涨幅。

这不是近似：取的是「该月末或之前最近一个交易日」的真实收盘价，
与预置窗口同一套取值规则，只是把可选起点限制到月粒度。
校验：用月末点位反推的 YTD 与快照逐项一致（99 个数值，最大偏差 0.005pt）。

> 精度坑：月末点位起初按定点 3 位小数存储，印尼/越南指数换算成美元后
> 数值不到 0.4，相对误差让反推涨幅与快照差 0.11 个百分点。改为 8 位有效数字后解决。

### jsDelivr 缓存坑

实测推送新版后云函数仍取到上一版（20 KB 旧快照）。jsDelivr 对分支引用缓存很久，
Actions 现在推送后主动调 `purge.jsdelivr.net`。云函数侧只做新鲜度上报、不换源重试——
purge 有传播延迟，一旦回退到 raw.githubusercontent 就是两次取数，必然超时。

### 现状

云函数：`get-snapshot` / `get-monthly` / `get-series`（均零依赖）。
`ingest` / `daily-sync` / `probe` 已被取代，可在控制台删除；
`ingest` 上的两个定时触发器也不再需要（留着只是每日空跑，无副作用）。

## P2 完成 + P3 首页（2026-09-20）

### 最终架构（绕开付费限制）

```
GitHub Actions（每日 UTC 22:00，无超时限制）
  └─ 跑 cloudfunctions/lib 下的同一套 Node 代码

  └─ 客户端首屏数据入口（集合默认权限禁止客户端直读，走函数免去权限配置）
```

预热后仅 1.3-1.8 秒），第二次触发时函数已热，天然充当重试。函数幂等。

## 第三轮：绕开代理补齐核心数据（2026-09-19）

用户按 TODO 执行 `env -u HTTP_PROXY ...` 后**东财仍然全部失败**。诊断发现是两层问题，
清环境变量对任何一层都无效：

| 层 | 状况 |
|---|---|
| macOS 系统代理 | `scutil --proxy` 中 HTTP/HTTPS/SOCKS 均指向 `127.0.0.1:10808`（Python urllib 会读，curl 不读） |
| **TUN 路由劫持** | 路由表 `128.0/1 → utun28`，比 `default` 更具体 → 全部流量强制进隧道，与环境变量无关 |

**结论：必须关闭代理软件或切到规则模式，`env -u` 解决不了。**

但与其让用户反复开关代理，改为**扩展源链**——找到三条境外 IP 可直连的新浪专用接口：

| 源 | 覆盖 | 历史深度 |
|---|---|---|
| `money.finance.sina.com.cn` CN_MarketData | A 股（上证、沪深300） | 1023 条（约 4 年） |
