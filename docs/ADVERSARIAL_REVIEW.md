## A1 🔴🟡 `*` 回退把两种单位混进同一个排名，而且正好混在榜首

**问题**

`index.js:146-162` 的 `val()`：某口径为 null 时退回 `r.local`，标 `*`，照常参与排序。
`detail.js` 同理。你的理由是「不让市场凭空消失」。

从金融角度这**根本站不住**，原因不是「单位不纯」这种洁癖，而是：
**排序是一个跨行比较操作，它要求所有行在同一个度量下**。混进来的行不是「稍微不同的口径」，
是完全不同的量纲。而且退回的方向是系统性的——缺汇率的恰恰是货币在贬值的新兴市场，
所以原币数**必然偏高**，必然往榜首跑。这不是随机噪音，是单边偏置。

**复现**

```bash
node -e '
const s=require("./dist/snapshot.json");
const rows=s.meta.map(m=>{const r=s.snapshot[m.code]["anchor:2022-10-12"]||{};
  let v=r.cny,fb=false; if(v==null){v=r.local;fb=v!=null;} return{c:m.country,n:m.name,v,fb};})
 .filter(r=>r.v!=null).sort((a,b)=>b.v-a.v);
rows.slice(0,8).forEach((r,i)=>console.log(`${i+1} ${r.c} ${r.n} ${r.v.toFixed(2)}%${r.fb?" *":""}`));'
```

实际输出（`美股熊市底以来 · 人民币口径`）：

```
1 埃及 埃及CASE30 +464.84% *      ← EGP
2 巴基斯坦 卡拉奇KSE100 +314.12% *  ← PKR
3 中国台湾 台湾加权指数 +260.67% *   ← TWD
4 韩国 韩国综合指数 +200.46%        ← 这才是人民币
5 意大利 富时MIB +177.73%
```

**一个「人民币口径」的榜单，前三名全都不是人民币。** `近3年` 窗口同样，前三名 5 个 `*` 里占 3 个。

**偏差有多大**——用你自己的数据算（只取汇率**确实有**的那一段，2024-03-20 起）：

| 市场 | 区间 | 原币 | 人民币 | 汇率拖累 |
|---|---|---|---|---|
| 埃及 CASE30 | 2024-03-20 → 2026-09-20 | +93.6% | +62.3% | **−31.3pt** |
| 巴基斯坦 KSE100 | 2024-03-20 → 2026-09-18 | +160.0% | +143.3% | −16.7pt |
| 中国台湾 加权 | 2024-03-20 → 2026-09-18 | +138.5% | +122.1% | −16.4pt |
| 越南 VNI | 2024-03-20 → 2026-09-18 | +44.1% | +28.1% | −15.9pt |

这还只是汇率**有数据**的 2.5 年。`美股熊市底以来` 跨的是 2022-10 至今，中间包含
EGP 2024 年 3 月的一次性大幅贬值（本表里 EGP 最早一条就已经是 47.05，而 2022 年 10 月
埃及镑远不在这个水平）。埃及那个 `+464.84%` 的人民币真值大致在 **+110% 到 +130%** 量级，
也就是说**显示值是真值的三到四倍，并且把它从第 7-8 名推到了第 1 名**。

**严重程度**：🔴 + 🟡。它既是算错数（数值差 3-4 倍），也是误导（把错的那个放在最显眼的位置）。
而且它精确地反转了产品的核心主张——「跨国比较不换算货币等于没比」——就在最该兑现主张的地方。

**修法**（推荐第 2 种）

1. ~~剔除出榜~~：你已经否决过，我同意否决。市场消失确实更糟。
2. **移出排名、保留展示**：口径不完整的行**不参与排序**，统一置于榜单下方一个独立分区
   「以下市场在本区间无可用汇率，仅列原币涨幅，不参与排名」。这样既不消失，也不污染名次。
   改动量：`index.js` 的 `ok/na` 二分改成 `ok/fb/na` 三分，约 20 行。
3. 顺带把窗口标题改成 `近3年 · 人民币口径 · 28 个市场参与排名`，把 n 说出来。

## A2 🔴 汇率增量逻辑断链：`partial` 是死代码，5 个市场的汇率每 30 天冻结一次

**问题**

`fx.js:99-101` 算出了 `partial`（「有数据但已落后 3 天以上、需要走备源补增量」的币种），
**然后再也没有被引用过**。`prevHadFrankfurter` 恒返回 `false`，也是死的。

实际执行路径是：`rest` 只收「完全没有数据」的币种（`fx.js:97`）。第一次构建之后，
TWD / VND / PKR / EGP / RUB / LKR 在 `prev` 里都有数据 → 不进 `rest` →
**currency-api 根本不会被调用** → 这几个币种的汇率**永久停在第一次构建那天**。

直到 30 天后 `STALE_DAYS` 的停更检查（`fx.js:92-95`）把它们整个删掉，
才重新落进 `rest`，触发一次**从 2024-03-20 开始的 950 次请求全量回补**——
也就是增量逻辑本来要避免的那件事。

**复现**（mock 掉 `./http`，用真实 `dist/fx.json` 当 prev，模拟隔天/半月/36 天后再构建）

```bash
node scripts/review/repro-fx-increment.js
```

实测输出：

```
=== 模拟 end=2026-09-21（prev 停在 2026-09-19） ===
currency-api 请求数: 0
TWD: 2026-09-19 -> 2026-09-19      ← 没动
EUR: 2026-09-18 -> 2026-09-21      ← 主源正常推进

=== 模拟 end=2026-10-05 ===
currency-api 请求数: 0
TWD: 2026-09-19 -> 2026-09-19      ← 还是没动，已经落后 16 天

=== 模拟 end=2026-10-25 ===
currency-api 请求数: 950           ← 触发全量回补
TWD: 2026-09-19 -> 2026-10-25
```

**后果**

在那 30 天里，`makeLevelFn` 的 `at(fxPairs[ccy], pt[0])` 会**静默返回一个最多 30 天前的汇率**：
区间终点用的是陈旧汇率，区间起点用的是正确汇率 → 涨幅**系统性偏差**，
而且 `canFx` 仍为 true、`level()` 仍返回数字，**界面上没有 `*`、没有任何提示**。

量级：TWD 月波动约 1%，EGP / RUB 月波动可以到 5-10%。也就是台湾的人民币口径会慢慢漂 1pt，
埃及、俄罗斯可以漂 5-10pt——并且是在你以为已经解决了这个问题之后
（`fx.js` 第 8-9 行的注释正是在讲这个失效模式）。

这条最恶劣的地方是**现有的任何检查都看不见它**：`verify-node-vs-python`、
`check-page-logic`、`check-detail-logic` 全都跑在同一份 `dist/fx.json` 上，
而这份文件是某次全量构建的产物。只有连续跑两天才会暴露。

**严重程度**：🔴。静默、持续、影响面 5 个市场、测试覆盖不到。

**修法**

```js
// fx.js：把已算好的 partial 接上
const toBackfill = [...rest, ...partial];
if (toBackfill.length) {
  // partial 只补自己的增量，不从 CCY_API_START 重来
  const fromFor = (c) => rest.includes(c)
    ? CCY_API_START
    : shiftDays(Object.keys(rates[c]).sort().pop(), -3);
  // fromCurrencyApi 需要支持按币种指定起点，或按 min(fromFor) 拉一次再合并
}
```
最小改动版：把 `fromCurrencyApi` 的 `from` 改成 `min(各 partial 币种的 last) - 3 天`，
一次拉完再 merge；日常只有几天的请求量。

**另外**：`STALE_DAYS = 30` 对「主源停发」是合理的，但对「我们自己忘了更新」太宽松。
建议把停更阈值分成两档：>7 天 → 在 `meta` 里打 `fxStale` 标记并在界面上标 `*`；
>30 天 → 才整个删除。这样即使增量再断一次，界面会诚实地退回原币并标注，
而不是拿陈旧汇率算出一个看起来正常的数。

## A3 🔴 详情页同屏两个互相矛盾的涨幅，最大差 40.49 个百分点

**问题**

详情页上下相邻两块：
- `detail.wxml:26` 的 `chartStat`（图表标题）由 `detail.js:146` 算：`pts[last]/pts[0] - 1`，
  `pts[0]` 是 **`get-chart` 裁剪后的第一个点**，即「`from` 当天或之后第一个采样点」。
- `detail.wxml:35-43` 的「各区间涨幅」直接读快照，快照的基准是
  **「`from` 当天或之前最近一个交易日」**（`snapshot.js:118-120`）。

两个方向相反。更糟的是 `buildChart` 对一年以前的数据做了**周采样**
（`snapshot.js:302-307`，同周只保留最后一个交易日），所以 `近3年`/`近5年` 的起点
会落在某个周末样本上，偏差被放大到整周。而且 `buildChart` 的 `cutoff = minusMonths(last, 60)`
把更早的点直接丢了——**即使改 `get-chart` 的取法，`≤from` 的那个点也不在文件里**。

**复现**（忠实复刻 `get-chart` 的 `findIndex(x => x >= from)` 裁剪后跑真实 `detail.js`）

```
详情页 近1月: 图表标题「2026-08-18 → 2026-09-18 · +1.27%」  vs 格子「+1.27%」   ✅
详情页 近3月: 图表标题「2026-06-18 → 2026-09-18 · -16.60%」 vs 格子「-16.60%」  ✅
详情页 近1年: 图表标题「2025-09-18 → 2026-09-18 · +87.53%」 vs 格子「+87.53%」  ✅
详情页 近3年: 图表标题「2023-09-22 → 2026-09-18 · +142.05%」vs 格子「+134.74%」 ❌ 差 7.31pt
```

`{近3年: 88, 近5年: 16, 近3月: 3, 近1年: 3}`，最大偏差：

| 指数 | 区间 | 口径 | 图表标题 | 格子 | 差 |
|---|---|---|---|---|---|
| 巴基斯坦 KSE100 | 近3年 | 原币 | +229.13% | +269.62% | **−40.49pt** |
| 韩国 KOSPI | 近3年 | 美元 | +163.96% | +155.71% | +8.25pt |
| 韩国 KOSPI | 近3年 | 人民币 | +142.05% | +134.74% | +7.31pt |

**为什么 STATUS 里写着「已验证一致」**：`scripts/check-detail-logic.js:18-23` 的
`get-chart` 桩**忽略了 `data.from`，永远返回整份文件**。也就是说那次验证
根本没跑到被测代码。而且只测了 `近1月`/`近1年`（`from` 恰好落在交易日、恰好在日采样区），

1. `buildChart`：`rows` 的筛选从 `p[0] >= cutoff` 改为「`cutoff` 之前最近的那一个点 + `>= cutoff` 的全部」，

## A4 🟡 走势图 x 轴按数组下标等距，而采样频率是混的 —— 时间轴被压扁

**问题**

`detail.js:178`：`x = (i) => padL + (W-padL-padR) * (i / (pts.length-1))`。按**下标**等距。

而 `buildChart` 近 1 年是**日采样**、更早是**周采样**。于是：

| 所选区间 | 周采样点数 | 日采样点数 | 最近 1 年占用宽度 | 它实际占的时间 |
|---|---|---|---|---|
| 近3年 | ~104 | ~250 | **约 70%** | 33% |
| 近5年 | ~208 | ~250 | **约 55%** | 20% |

也就是说，5 年走势图里最近一年横向占了一半以上。所有「几年横盘、最近拉升」的形态
都会被夸大成「长期陡峭上行」，而早期的大波动被压成一小段。

**复现**：打开任一指数详情页，切「近5年」，看折线的拐点位置与 `sampleNote` 标注的
`XXXX-XX-XX 之前为每周采样` 的日期对不上——那条标注告诉你分界在哪一年，
但图上那个分界点在正中偏右，而不是在「1/5 处」。

**严重程度**：🟡。不算错数，但它是一张**画错的图**，不是「缺功能的图」。
界面上「如实标注周采样」并不能补救——读者看的是形状，形状是错的。

**修法**：`x` 改成按日期线性映射：

```js
const t0 = +new Date(pts[0][0]), t1 = +new Date(pts[pts.length-1][0]);
const x = (i) => padL + (W-padL-padR) * ((+new Date(pts[i][0]) - t0) / (t1 - t0));
```
四行。改完周采样区自然变稀疏（这是对的：信息密度本来就低），日采样区自然变密。

## A8 🟡 「今日」窗口：你的反驳站不住，但结论（保留）是对的

**你的反驳原话**：「所有窗口都有同样错位，只是分母大显得小」。

**这个推理错了**，而且错在关键处。一天的端点错位对不同窗口不是「同一种误差除以不同分母」：

- 对 `近3年 +134.74%`：挪一天大约改变 1-2pt，相对误差约 1%。是**噪音**。
- 对 `今日`：挪一天就是**换了一个完全不同的事件**，相对误差 100%+。是**信号本身**。

分母大小不是修辞，它就是噪音与信号的分界线。

而且真正的问题比埃及那一天大得多，你没提到：**`d1` 的起点是
`series[len-2]`（上一个交易日），不管它离今天多远**（`snapshot.js:97,99`）。
长假之后「今日」就是一个跨假期的累计涨幅。

**复现**

```bash
node -e '

const out=[];
for(const m of meta){const a=ser[m.code];
 for(let i=1;i<a.length;i++){const g=(new Date(a[i][0])-new Date(a[i-1][0]))/864e5;
  if(g>=5)out.push([m.country,m.name,a[i][0],a[i-1][0],g,(a[i][1]/a[i-1][1]-1)*100]);}}
out.sort((x,y)=>Math.abs(y[5])-Math.abs(x[5]));
out.slice(0,6).forEach(r=>console.log(`${r[0]} ${r[1]} ${r[2]}（上一交易日 ${r[3]}，隔 ${r[4]} 天）「今日」= ${r[5].toFixed(2)}%`));

```
```

巴基斯坦 KSE100 2023-11-01（隔 30 天）「今日」= +16.59%
中国台湾 台湾加权 2025-04-07（隔 5 天）「今日」= -9.70%
中国 深证成指 2024-10-08（隔 8 天）「今日」= +9.17%

```

2024-10-08 那天，「今日」榜的前三名会是创业板 +17.25%、深证 +9.17%、沪深300 +5.93%
——**一个纯粹的日历产物**，而当天其他所有市场都是真实的单日涨跌。
按国家分布：中国 64 次、香港 62 次、巴基斯坦 49 次、印尼 19 次…… 这不是边缘案例，

**结论**：评审建议「砍掉今日」的**理由**不对（不是因为差一天），

**修法**（三条都很便宜）

2. `starts.d1` 的间隔 > 4 个自然日时，行内标注 `（跨 8 天）`。
   `meta` 里加 `d1Span = daysBetween(prevTradingDay, asof)`，客户端直接渲染。
3. **不要让 `今日` 当默认窗口**（现在默认是 `ytd`，这点你做对了），
   并且 `今日` 窗口下的结论条不要给「中位数」——一天的横截面中位数没有意义。

## A14 🟡 名次变化 Δ 的语义：对「今年以来」对，对滚动窗口是**另一个问题的答案**

**问题**（你的第 4 点）

`buildRankDelta`（`snapshot.js:161-188`）用 `endShiftDays: -7` 重算一次快照。
`buildSnapshot` 里 `endShiftDays` 的做法是**砍掉终点之后的数据**（`snapshot.js:86-91`），

- `ytd`：起点仍是去年 12-31，终点退 7 天。→ **「一周前的今年以来排名」**。语义正确。
- `m1`：起点跟着退 7 天。→ 比的是「[T-37, T-7] 的排名」与「[T-30, T] 的排名」。

- `anchor:*`：起点固定，语义同 `ytd`，正确。

「一周前如果看近1月榜，谁在前面」本身是个有意义的问题，

2. `buildRankDelta` 里对两次快照取**参与池的交集**再排名，消除池变动的假信号。约 6 行。
3. 可选：只对起点固定的窗口（`ytd` / `anchor:*`）显示 Δ，滚动窗口不显示。我不推荐——

它不是无副作用的：它会 `cloud.init` + 写 `index_snapshot` 集合。如果将来有人
（包括未来的你）以为数据库里那张表是权威的，就会拿到用旧代码算出的数。

**修法**：删目录、删触发器。`ingest` / `probe` 同理。

## A19 🟢 `fx.json` 携带 8 个没有任何指数使用的币种

`dist/fx.json` 1.5 MB，里面有 MYR / CZK / PLN / DKK / SEK / ISK / PHP / NOK / THB / LKR，
而 `CURRENCIES` 里一个都没有。原因是 `fx.js:75` 无条件继承 `prev` 的全部币种。

所有 `fxReason` 会从 `baseline` 翻成 `gap`，`about`/展开里的说明文案跟着全错。

**修法**：`fx.js:75` 加 `if (!need.has(c)) continue;`。一行。
`fxBaseline` 改成「`CNY` 的起点」——`canFx` 的定义本来就依赖 CNY，语义也更直白。

## A20 🟢 `onRange` 失败后，区间标签与图表数据错配

`detail.js:100-104`：`setData({rangeIdx})` 在 `await loadChart()` **之前**。
`loadChart` 抛错时 `rangeIdx` 已经改了、`this.chart` 还是旧区间的。
`catch` 只设 `chartStat/noCur`，但之后任何一次 `onCur()` 都会用旧数据重新 `render()`，
把旧区间的曲线和日期挂在新区间的标签下面。

**修法**：成功之后再 `setData({rangeIdx})`；失败时回滚。

## A21 ✅ 月末点位的跨月边界 —— **这条没问题**

我合成了两个市场（A 交易到 1/2、B 停在 12/31）跑 `buildMonthly` + `buildYearly`：

```
months 末三个: 2025-11  2025-12  2026-01
A local: 100 100 100     B local: 100 100 100
A 逐年 2026 年初至今: 0%  B 逐年 2026 年初至今: 0%
```

B 在 2026-01 没有交易，`cutoffs` 取 `min(月末, maxDate)` = 2026-01-02，
`at()` 回退到 2025-12-31，`年初至今 = 0%` —— **这是正确答案**（这一年确实什么都没发生）。
`buildYearly` 的 `i0 = idxOf(y-1 月12)`、`i1 = 当年取 months.length-1`，跨年也对。

唯一不优雅的是：月份选择器会列出一个该市场尚未交易的月份（`2026-01`），
选它等于选上个月末。属于 🟢，不改也行；要改就是给当月列加 `partial: true`，
picker 里标成 `2026-01（截至 01-02）`。

## A22 ✅ 8 位有效数字 —— **这条也没问题，余量很大**

```
100          -> 100          相对误差 0
7650.5       -> 7650.5       相对误差 0
0.0715       -> 0.0715       相对误差 0
99999999.5   -> 100000000    相对误差 5.0e-9   ← 最坏情况
```

最坏相对误差 5e-9，起止两点合成后约 1e-8，折算到涨幅上是 **1e-6 个百分点**。
你之前踩的定点 3 位小数坑（相对误差 1.3e-3）和现在差了 5 个数量级。
甚至 6 位有效数字都足够（相对误差 5e-7 → 涨幅误差 1e-4pt，远小于显示的 2 位小数）。
8 位是安全的过度设计，不用动。

## B1 这个榜单少了什么会让专业人士不信任它

按「第一眼就会发现」的顺序，五条，都点名：

**一、没有区间长度，因而没有年化。**
下拉里 `近1月 / 近3年 / 疫情底以来 / 关税冲击日以来` 平级排列，一个是 30 天，
一个是 6.5 年。看盘的人切到「近3年 +134.74%」的第一反应是「年化多少」，
产品没给，他就得自己心算——那一刻他已经在把这个产品当玩具了。
成本最低、收益最大的一条。见 A15。

**二、榜首那几行带着 `*`，而 `*` 的解释在 30 行之下。**
专业读者看到脚注符号会立刻找脚注。找不到 → 不信。找到了 → 发现是「这一行其实是另一个货币」
→ 更不信。见 A1。

**三、没有参与数量。**
「N 涨 N 跌 · 中位数 X%」不说 N 是多少个市场，也不说有多少个被剔除了。
切到近5年时 N=2，统计量照给。见 A17。

**四、价格指数不含股息这件事被当成免责而不是口径。**
专业读者知道 MSCI 有 Price / Net / Gross 三条线，他会问你用的是哪条。
「仅在长周期窗口提示一行小字」的答案是「我们用的是 Price，但我们希望你别在意」。
见 B5——这件事**会改变名次**，我算给你看了。

**五、没有「这份数据是什么时候、由谁、怎么来的」的一等公民位置。**
`get-snapshot` 算了 `stale` 却没人读（A13）；`meta.source` 藏在展开里；
构建失败静默。专业用户对数据管道的信任建立在「它坏的时候会告诉我」，
而不是「它一直看起来没坏」。

次一级但也会被注意到的：**同一国家多个指数**（A16）、
**走势图没有零轴与刻度**（B6）、**详情页两个数字打架**（A3）。

## B2 只给涨幅不给风险，是不是根本性缺陷？

**不是根本性缺陷。** 产品的问题定义是「哪个国家涨得多」，那是一个完整、自洽的问题，
它不需要风险就能回答。变成缺陷是在你暗示「所以你应该看哪个国家」的那一刻——
而你恰好因为类目审核不做推荐，所以边界是守住的。

**但年化比风险更紧迫**（B1 第一条）。风险是加分项，年化是及格线。

**如果只补一项，补最大回撤，不要补波动率。** 三个理由：

1. **单位相同。** 最大回撤和涨幅都是 %，可以直接并排：
   「近3年 +167.8%，期间最多回撤 −38.6%」。读者不需要学任何新概念。
   而「年化波动率 18.4%」对绝大多数中文用户是一个不传递信息的数字。
2. **是区间内的量。** 波动率需要选滚动窗口、选年化方式，每个选择都要解释；
   最大回撤在你已经选定的区间内唯一确定，没有自由参数。
3. **计算成本为零。** 构建侧对日线单遍扫描 O(n)，日线本来就在手。
   快照增加 33 × 3 口径 × 8 窗口个数字 ≈ 几 KB，**3 秒预算完全不受影响**
   （现在快照 52 KB / 1.5 秒，加这些到不了 56 KB）。

我跑了一遍近3年原币：

| 市场 | 涨幅 | 最大回撤 |
|---|---|---|
| 韩国 KOSPI | +167.8% | **−38.6%** |
| 日本 N225 | +93.9% | −26.3% |
| 纳斯达克100 | +94.7% | −22.9% |
| 标普500 | +71.8% | −18.9% |
| 德国 DAX | +60.9% | −16.0% |
| 香港恒生 | +38.0% | −20.0% |
| 上证 | +25.1% | −14.7% |

韩国的 +167.8% 背后是 −38.6% 的回撤——这一行让榜首从「最好的市场」变成
「最好但最颠的市场」。这就是一个数字能买到的全部价值，而它免费。

**手机上怎么放：不要加一列。** 375px 已经有 `#` / 国名+指数名 / 涨幅 / 色条四块。
放两个地方：

- **展开行里**（已有交互，`index.js:onTapRow`）：在「涨幅 = 原币 × 汇率」下面加一行
  「期间最大回撤 −38.6%（2025-11-04 → 2026-02-13）」。
- **色条上叠一条回撤影子**：涨幅色条右侧延伸出一段更浅的同色条表示回撤深度。
  不占额外高度，扫一眼就看出「谁涨得稳、谁涨得颠」。这是整个产品里
  最接近「信息可视化」而不是「装饰」的一笔。

## B3 中位数是不是合适的概括统计量？

**中位数本身是对的**（33 个高度相关的序列，均值会被尾部拽走；你又有长尾市场，
更不能用均值）。但它**不是这里最有信息量的数**，而且现在的用法有两个问题：

1. **没说 n。** 见 A17。
2. **只给中心，不给离散度。** 「12 涨 0 跌 · 中位数 +1.8%」完全看不出
   这是「大家都涨一点」还是「有的 +30% 有的 −25%」——而后者才是读者真正想知道的：
   **今年是贝塔行情还是选国行情？**

**推荐换成分位数三元组**，一行三个数：

```
33 个市场 · P25 −3.9%  中位 +1.8%  P75 +7.1%  （四分位距 11.0pt）
```

这是我用真实数据算的今年以来人民币口径。11pt 的四分位距立刻告诉你
「今年全球是普通分化，不是普涨也不是普跌」。而「涨跌家数 + 中位数」说不出这件事。

成本：构建侧三行，客户端换个模板字符串。

**如果只能保留两个数**：中位数 + 四分位距。涨跌家数是三者里信息量最低的
（它是中位数的一个粗糙投影：中位数为正时涨家必然过半）。

## B4 红涨绿跌要不要做成可切换？

**不要做。这条你的判断是对的，属于过度设计。** 三个理由：

1. **目标用户是中文用户。** 这个产品默认人民币口径、中文界面、微信小程序渠道。
   为一个假想的「习惯欧美配色的用户」加一个设置项，是在为少数派增加所有人的认知负担。
2. **可切换会污染分享。** 这个产品的终局是被截图转发到群里。
   同一张图在两个人手机上颜色相反，就没法讨论了。固定配色是分享型产品的必要属性。
3. **颜色本来就不该是唯一编码，而你已经做对了。** `+`/`−` 前缀（`index.js:169`）、
   色条左右分方向（`index.wxml:86-87`）——即使完全看不见颜色也能读懂。
   这已经解决了真正的问题（东亚男性约 5% 有红绿色觉障碍），而配色方向解决不了任何问题。

**唯一值得做的**：`about` 页加一行「本表采用中国习惯：红涨绿跌」。一句话，成本为零，
把潜在的误读变成已披露的约定。

## B5 「价格指数不含股息」的披露力度够吗？

**不够，而且有一个实打实的 bug（A12：默认窗口完全没有提示）。**
但「再加一行小字」不是答案。

**因为它会改变名次。** 我用你 `about` 页自己列的股息率量级（英 4% / 日 2% / 美 1.3%）
加上其余市场的常见档位（**以下是示意值，不是数据**）做了一次近3年人民币口径的重排：

```
价格榜#1  韩国     134.7%  →  含息 147.6%   含息榜#1
价格榜#2  美国(NDX) 78.7%  →  含息  82.5%   含息榜#2
价格榜#3  日本      67.0%  →  含息  77.2%   含息榜#3
价格榜#4  德国      58.7%  →  含息  73.5%   含息榜#4
价格榜#5  美国(SPX) 57.7%  →  含息  63.9%   含息榜#5
价格榜#6  英国      37.8%  →  含息  55.0%   含息榜#7  ⚠️ 降 1
价格榜#7  巴西      36.3%  →  含息  62.3%   含息榜#6  ⚠️ 升 1
```

一个免责声明不足以承载 17 个百分点。

**推荐做法**（按成本递增，我推荐做到第 2 步）

1. **口径进标题，不进脚注。** 窗口标签改成 `近3年 · 人民币 · 价格指数`。
   读者第一眼就知道这是哪条线，而不是读到底部才发现。成本：一个字符串。
2. **在展开行里给第二个数。** 维护一张 **33 行的静态股息率常数表**（`indices.js` 加 `dy` 字段），
   展开时显示「按 4.0%/年股息回补 ≈ +55.0%」。
   - 成本：一张常数表 + 构建侧一次 `Math.pow`。**3 秒预算零影响**，
     快照增加 33 × 3 × 8 个数字。
   - **必须标注年份与来源**：「股息率为各交易所公布的 2025 年指数股息率，静态假设」。
     静态股息率会过期，标了年份它就是一个诚实的近似，不标就是一个会烂掉的数。
   - 不要把它做进主榜排序——那会让产品声称自己是总回报口径，而它不是。
     放在展开里，作为「知道这件事的人可以自己折算」的工具。
3. （不推荐）真去抓总回报指数：多数总回报指数不公开免费日线，且会把数据源复杂度翻倍。

## B6 走势图加什么值得，加什么是负担

**先修，再加。** 当前这张图有一个必须先修的错误（A4）：x 轴按数组下标等距，
而采样频率是混的，导致近5年图里最近一年占了 55% 的宽度。
**在修好之前，加任何东西都是在给一张画错的图做装饰。**

修完之后，按性价比：

### 值得加

1. **归一化为净值曲线（区间起点 = 100）。** 这一条的收益被低估了：
   - 切换人民币/美元/原币时形状直接可比（现在切口径会让 y 轴量纲整个变掉）。
   - 解决量纲问题：越南 VNI 换算成美元约 0.07，标普 7650，同一套绘图代码画它们
     现在靠 `lo/hi` 自适应，但 y 轴上没有任何数字，读者不知道自己在看什么尺度。
   - 成本：`vals` 除以 `vals[0]` 乘 100，两行。
2. **一条 100 基准虚线 + 右端当前值标注。** 有了基准线，「跌破起点」这个最重要的
   视觉事实才成立。现在的图无论涨跌都是一条悬空的线。成本：约 8 行。
3. **区间内最高/最低点打两个小圆点 + 数值。** 这是「最大回撤」的视觉版本，
   和 B2 的建议共用同一次扫描。成本：约 10 行。

### 不值得加

1. **交互式十字光标 / tooltip。** 手机上手指会盖住取值点；而且要么在 canvas 上
   自己做 hit-test（几十行 + 触摸事件），要么走 `setData` 往返（卡）。
   收益是「看某一天的具体值」——这个需求在一个**国家级涨幅排行**产品里几乎不存在。
2. **完整坐标轴 + 网格。** 375px 宽、你现在的图高大约 160px，加 y 轴刻度要吃掉
   左侧 40px 和一部分高度，换来的是读者本来就不关心的绝对点位。
   归一化 + 基准线已经给了 90% 的定位信息。
3. **多指数叠加对比。** 诱人，但它会把产品从「国家排行」推向「个股/标的比较工具」，
   这既偏离主语，也更靠近金融类目审核的敏感区。
4. **蜡烛图。** 你只有收盘价，画不了，也不该画。

# 最严重的三个问题

## 第一 · A1 —— 「人民币口径」榜单的前三名不是人民币

`近3年` 和 `美股熊市底以来` 两个窗口下，人民币榜的前三名全部是原币数（埃及、巴基斯坦、

**显示值是真值的三到四倍，并把它从第 7-8 名顶到了第 1 名**。

选它做第一不是因为数值偏差最大，是因为它**精确地反转了产品的核心主张**：
「跨国比较不换算货币等于没比」——而它没换算的恰恰是榜首。
任何一个专业读者点开「近3年」看到埃及第一，会立刻知道这个榜单不能用。

你的原始理由（不让市场消失）是对的，被否决的只是**让它继续参与排序**这一步。

## 第二 · A3 —— 详情页同一块屏幕上两个互相矛盾的涨幅，最大差 40.49pt

韩国详情页「近3年」：图表标题 `+142.05%`，正下方的格子 `+134.74%`。
巴基斯坦原币口径差 **40.49 个百分点**。全量扫描 110 条不一致。
「近5年」更糟：格子诚实地写 `—`，图表标题给了一个 4.06 年的 `+160.35%`，
直接违反产品自己写在 README、about 页和源码注释里的第 3 条主张。

选它做第二，是因为**它是唯一一类用户自己就能当场验伪的错误**。
前一条要有汇率知识才看得出来；这一条只需要眼睛向下移动 3 厘米。

而且 `check-detail-logic.js` 的 `get-chart` 桩忽略了 `from` 参数，
所以 STATUS 里那条「图表数据与榜单口径一致性 ✅」是无效验证——
**这是你问的「验证本身有问题」那一类，确实有一个。**

## 第三 · A2 —— 汇率增量逻辑断链，5 个市场的汇率每 30 天冻结一次

`fx.js` 里算好的 `partial` 从未被使用。实际行为（我 mock 网络模拟了三个日期，
不是推断）：TWD / VND / PKR / EGP / RUB / LKR 在第一次构建之后**再也不更新**，
一直到 30 天后被停更检查整个删除、再触发一次 950 次请求的全量回补，然后循环。

在那 30 天里，这些市场的人民币/美元口径用的是**最多 30 天前的终点汇率**配**正确的起点汇率**，
`canFx` 仍是 true，界面上**没有 `*`、没有任何提示**。EGP、RUB 的月波动能到 5-10%。

选它做第三，是因为它的三个属性叠在一起：**静默**（用户和你都看不见）、
**持续**（每天都在发生）、**测试盲区**（所有检查脚本都跑在同一份 `dist/fx.json` 上，
连续跑两天才会暴露）。`fx.js` 第 8-9 行的注释恰好就是在讲这个失效模式——
代码知道这件事的危险，但接线没接上。
