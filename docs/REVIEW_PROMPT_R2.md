## 第一件事：审查测试，而不是代码

在读任何业务代码之前，先把上面四个检查脚本读一遍，逐个回答：

1. **这个断言真的会失败吗？** 挑几条断言，把被测代码改坏，看它是否变红。
   （我自己这么做时发现过两次断言太弱：一次是 `Number.isNaN(undefined)`
   是 false 所以测不出未初始化，一次是测试无意中让页面重新加载成功了。）
2. **桩是否忠实？** `check-detail-logic.js` 里 get-chart 的桩、
   `check-cdn-hedge.js` 里 https 的桩——它们和真实实现有没有行为差异？
   上一轮就是栽在这上面。
3. **覆盖的是不是真实路径？** 比如 `check-detail-logic.js` 复用同一个
   页面实例跑多个用例，实例上的 `this.snap` / `this.m` / `this.chartCache`
   会跨用例残留。哪些用例因此测的其实是另一种状态？
4. **verify-node-vs-python.js 的容差 0.011 个百分点**是怎么定的？
   这个容差会不会掩盖真实的算法分歧？

如果你认为某个检查是假的，**请直接把它改成会失败的版本并跑给我看**。

## 第二件事：重点攻击最近这几处修复

**下面是我自己最没底的地方，按不确定程度排序。
不要因为我列出来就以为已经想清楚了——恰恰相反。**

### 1. cdn.js 的对冲请求可能让一次页面加载混用两个数据源

这是我最担心的一条，而且是**我自己引入的新风险**。

原来两个源串行尝试：主源 raw.githubusercontent，备源 jsDelivr。
因为免费版函数 3 秒超时而两个源各给 2400ms，主源一挂起备源就发不出去，
线上 20 次调用只有 5 次成功。我改成了对冲：主源 900ms 还没回来就并发
点燃备源，谁先回用谁。成功率升到 18/20。

问题是：**jsDelivr 会缓存分支→commit 的解析结果，可能回上一版数据**
（这一点在 cdn.js 的注释里有详细记录，是实测过的）。对冲之后：

- `get-snapshot` 可能走 raw（今天的数据）
- 同一次页面加载里的 `get-chart` 可能走 jsDelivr（昨天的数据）

于是榜单的数字和图表的曲线来自不同日期的构建。请判断：

- 这个风险有多大？`freshEnough()` 的 36 小时阈值挡得住吗？
- 它会以什么形式被用户看见？（提示：详情页的标题读快照、曲线读 chart，
  正是上一轮 A3 那对冤家）
- HEDGE_AT=900ms / BUDGET=2500ms 这两个数是我拍的，有没有更有道理的取法？
- 有没有既保住成功率又保证同源的办法？（比如让快照带上构建 id，
  图表请求带着它，对不上就重取——代价是什么？）

### 2. detail.js 的请求令牌

`onRange` 里 `await` 之后的 `render()` 读的是渲染那一刻的 `rangeIdx`，
不是发起时的，所以连点区间会拿旧曲线配新窗口的数值。我加了令牌。

请攻击：
- 令牌只保护了 `onRange`。`onCur`（切口径）是同步的，但它 `render()` 时
  用的 `this.chart` 可能是另一个在途请求刚写进去的。有洞吗？
- `loadChart` 的 `chartCache` 按区间 key 缓存，但**不按口径**缓存——
  因为一份 chart 文件里同时含三种口径。切口径不重取，对吗？
- 下拉刷新 / 页面返回再进入 时，缓存和令牌的状态对吗？

### 3. 排行榜的三分法（ok / 仅原币 / 数据不足）

上一轮最严重的一条：缺汇率的市场用原币值混进外币榜并占据榜首
（修复前「近3年·人民币」的前三名全不是人民币）。现在改成口径不完整的行
移出排序、单列一区，标题写出参与数。

请判断：
- 「28 个市场参与排名」+ 下方「4 个仅原币」这种呈现，
  会不会让用户把两个区当成一个连续的榜单？
- 被移出排名的恰恰是货币在贬值的新兴市场（台湾/埃及/越南/俄罗斯）。
  **把它们排除，本身是不是另一种系统性偏差**——榜单变成了
  「只含有汇率数据的市场」，而这个集合并不随机？
- 这 4 个市场缺的是 2024-03-20 之前的汇率（免费汇率源的起点）。
  短窗口它们是参与排名的，长窗口才掉队。用户切窗口时会看到榜单
  成员数变化，这个体验怎么解释才不别扭？

### 4. 频率校验截断了巴基斯坦的历史

`build-data.js` 发现巴基斯坦 2023 年及以前是月频（每年 42 条），
判定为不可与日频同榜，截断后日频从 2024-01-01 起，丢弃 74 条。
后果是它在「近3年」「近5年」显示「数据不足」。

请判断：SPARSE_THRESHOLD=180 这个阈值合理吗？有没有别的指数
正踩在边界上？「截断」和「保留但标注」哪个对用户更诚实？

- 扩展层 14 个市场当前拿不到，已决定维持 27 国 / 33 指数，
  不要把「补齐数据」当建议。

  两者都不可用也不打算绕过，别再提。
- 以下增强项已知且已决定推后，**不用再提一遍**：年化/CAGR、四分位距、
